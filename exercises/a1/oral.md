## 必会

**Q1** `a = [1, 2, 3]; b = a; b.append(4)` 之后 `a` 是什么？为什么？想真正复制一份该怎么办？

> [!note]- 参考答点
> `a` 是 `[1, 2, 3, 4]`。`b = a` 没有复制，只是让两个名字指向**同一个列表对象**。
>
> 要复制：`a.copy()`（浅拷贝，只复制外层）。外层里面还套着可变对象时得用 `copy.deepcopy(a)`。
> 张量同理：`x2 = x` 不复制数据，`x.clone()` 才复制。
>
> （这条把 §0.3 和 §8 的浅拷贝合成一题。）

**Q2** `a = [[1, 2], [3, 4]]; b = a.copy(); b[0].append(99)` 之后 `a` 是什么？为什么？

> [!note]- 参考答点
> `a` 是 `[[1, 2, 99], [3, 4]]`。`a.copy()` 只复制外层那个列表，内层的 `[1, 2]` 还是**共享**的
> 一个对象，所以通过 `b[0]` 改它，`a[0]` 看得见。
>
> 要彻底独立得用 `copy.deepcopy(a)`。

**Q3** 外层拿着数据集 `X`、`y`，内层写成 `for X, y in loader:` 会发生什么？症状是什么？
为什么这个坑在 C++ 里遇不到？

> [!note]- 参考答点
> Python 的 `for` **不创建新作用域**，循环变量就是外层那个名字。第一个 epoch 结束后，
> `X`、`y` 已经被最后一批样本替换，数据集本身没了。
>
> 症状：第二个 epoch 起只在那一小批样本上训练，参数收敛到一半就停住，**全程不报错**。
>
> C++ 的 `for` 自己开作用域，循环变量出了循环就消失，所以那个坑遇不到。
> 写法上把循环变量改名，例如 `for X_batch, y_batch in loader:`。

**Q4** `self.w = torch.randn(3)` 和 `self.w = nn.Parameter(torch.randn(3))` 有什么区别？
框架靠什么机制知道 `self.w` 是参数？

> [!note]- 参考答点
> 前者只是普通属性，不会被 `parameters()` 收集，优化器看不见它，`.to("cuda")` 也不会搬它、
> `state_dict()` 也不保存。后者会被登记成参数。
>
> 机制：`nn.Module` 重写了 `__setattr__`（§4.3），给属性赋值时会被拦截——值是 `nn.Parameter`
> 就登记进参数表，值是 `nn.Module` 就登记进子模块表。所以那一句不只是赋值。
>
> 配套的一条：子类里必须调 `super().__init__()`，因为它负责建那张登记表；漏掉的话
> `parameters()` 返回空，优化器拿到空列表，训练时参数一动不动，**而且不报错**。

**Q5** `net(X)` 和 `net.forward(X)` 有什么区别？为什么必须写前者？

> [!note]- 参考答点
> `net(X)` 走的是 `nn.Module.__call__`，它依次触发 forward pre-hook、`forward`、forward hook。
>
> `net.forward(X)` 直接调方法，绕过了这层 hook，于是挂在 hook 上的功能失效：
> `torch.compile`、梯度检查点、各种调试与可视化工具。
>
> 能跑通，但框架的部分能力没了，所以统一写 `net(X)`。

## 了解

**Q6** `self` 为什么必须显式写在参数列表第一个，而 C++ 的 `this` 不用？

> [!note]- 参考答点
> Python 的方法就是普通函数，绑定在类上；`m.forward(x)` 实际执行的是 `Model.forward(m, x)`——
> 实例是当作第一个**位置参数**传进去的，所以必须有个名字接住它，那就是 `self`。
>
> C++ 的 `this` 是编译器隐式提供的，不在参数列表里出现。名字 `self` 只是惯例，
> 写成别的也合法，但没人这么做。

**Q7** `Vec2(1, 2) == "abc"` 时，`__eq__` 里应该返回什么？为什么不直接返回 `False`？

> [!note]- 参考答点
> 返回 `NotImplemented`（不是 `False`，也不是抛异常）。它的意思是"我不认识对面这个东西，
> 你（解释器）去问问对面"。
>
> 解释器收到之后会去试 `other.__eq__(self)`；两边都说不认识，才落到默认行为——同一个对象才相等，
> 于是最终得到 `False`。
>
> 直接返回 `False` 会堵死对面类的机会：以后另一个类声明"我能和 `Vec2` 比较"，`Vec2` 这边一口回绝，
> 对面永远没机会参与。
>
> （别把它和 `NotImplementedError` 搞混，后者是个异常。）

**Q8** 要写一个"每次吐一批数据"的函数，用 `yield` 还是 `return`？
把 `yield` 写成 `return` 会看到什么症状？

> [!note]- 参考答点
> 用 `yield`。带 `yield` 的函数是生成器函数：调用它一行都不执行，只返回一个生成器对象；
> 第一次迭代才跑到第一个 `yield` 然后停住，下次从停的地方继续。
>
> 写成 `return` 的话函数只返回第一批就结束，`for` 循环跑一次就停，**而且不报错**——
> 症状是"训练好像只跑了一批"。
>
> 判断标准：要"一次给一个、可以边算边给"就用 `yield`；要"算完一次性给"就用 `return`。

**Q9** `with` 块里抛异常了，`__exit__` 还会被调用吗？`with torch.no_grad():` 里抛异常会怎样？

> [!note]- 参考答点
> 会。`with` 进入时调 `__enter__`，离开时调 `__exit__`，**正常离开和抛异常都调**。
> `__exit__` 返回 `False` 表示不吞掉异常，异常继续往外抛。
>
> 所以 `with torch.no_grad():` 块里炸了，梯度记录状态照样会恢复。
> C++ 里对应 RAII：构造时获取资源，析构时释放。

**Q10** `@logged` 写在一个函数上面，等价于什么写法？`@property` 又是干什么的？

> [!note]- 参考答点
> 装饰器就是"把下面那个函数传给一个函数，用返回值替换它"。所以：
>
> ```python
> @logged
> def add(a, b): ...
> ```
>
> 等价于 `def add(...)` 之后写 `add = logged(add)`。没有别的魔法。
>
> `@property` 让方法能当属性读：写 `foo.shape` 而不是 `foo.shape()`。它和 §4 的
> `__get__` / `__set__`（描述符协议）有关，`@property` 本身就是用描述符实现的。
